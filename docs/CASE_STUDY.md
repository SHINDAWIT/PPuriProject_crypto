# 환경 변경에 대응한 암호 모듈 개발·연동 사례

[처음으로](../README.md) · [검증 결과](VALIDATION.md) · [협의 기록](COMMUNICATION.md)

## 목적과 담당 범위

연구실에서 보유한 기존 C 기반 ARIA 모듈을 재사용해 Edge의 Node-RED와 수신 측 Java Bridge에서 호출할 수 있도록 연동 모듈과 바이너리 전달 구성을 준비했다. 암호 알고리즘 자체를 새로 발명·개발한 과제로 설명하지 않는다.

나는 협력사에 적용 구간, 직렬화 시점, 데이터 타입, 실행 이미지, Java 버전과 호출 위치를 질문했다. 회신 정보를 개발에 전달하고, 전달본의 애드온·wrapper·예제·설명 누락 가능성을 검토했다. 문서·API 불일치에 대한 점검과 수정, 대상환경 재빌드·시험을 AI 개발도구에 요청했고, 개발된 모듈을 협력사에 전달했다.

코드 작성·수정·시험·패키징에는 AI 개발도구를 활용했다. Git 계정만으로 모든 코드를 직접 수작업 작성했다고 귀속하지 않는다. 동기와 공동 진행한 기록은 있지만 동료의 세부 구현 분담과 기여율은 확정하지 않았다.

## 1. 정보가 변경되거나 구체화될 때 빌드 기준 다시 확인하기

| 쟁점 | 당시 정보와 후속 확인 | 대응과 판단 범위 |
|---|---|---|
| Node-RED 이미지 | 초기 회신은 latest, 후속 회신은 4.0.5와 고정 digest | 재현 가능한 빌드 대상은 고정 이미지로 구체화. latest가 실제로 다른 이미지였다고 단정하지 않음 |
| Java 런타임 | 초기 Spark Java 8, 후속 회신은 Java 21 마이그레이션 완료. Broker Java 8, Bridge Java 21 | Spark·Broker·Bridge를 구분하고 JNI를 실제 로드할 Bridge의 Java 버전을 확인 |
| payload 타입 | 메일에는 Object 생성 후 후속 단계로 전달한다고 설명. 저장소 분석에는 송신 직전 JSON.stringify가 있다고 기록 | 생성 시점과 암호화 삽입 지점의 타입을 구분. 원본 Flow 전문을 이 공개본에서 재검증한 것은 아님 |
| 호스트와 컨테이너 | Ubuntu 호스트 안에서 Node-RED 컨테이너 실행 | native 바이너리의 기준은 모듈을 로드하는 실행환경. Edge musl과 Bridge glibc 바이너리 분리 |

“사양이 계속 달랐다”는 경험은 공개 설명에서 **초기 정보의 변경·구체화에 대응해 실제 실행 기준을 확정한 과정**으로 표현했다. Java 마이그레이션은 실제 변경으로 회신됐고, latest→digest는 이미지 식별을 명확히 한 경우다. 모든 차이를 협력사의 오류나 장애 원인으로 단정하지 않았다.

이 과정에서 확인되는 나의 활동은 필요한 정보를 다시 질문하고, 목적에 필요한 버전·구성요소 확인 범위를 좁힌 일이다. libc 차이와 대응 구조를 혼자 최초 진단했다고 쓰지 않는다.

## 2. 기존 모듈과 언어별 호출 경계 구성

~~~text
공통 C ABI
  ├─ Node N-API addon → JavaScript wrapper → Node-RED 호출 지점
  └─ Java JNI → API JAR → 별도 Bridge 프로세스
~~~

기존 C 코어를 재사용하고 공통 C ABI와 언어별 어댑터를 연결한 구성이 저장소에 남아 있다. Node와 Java에 암호 알고리즘을 각각 중복 구현하는 형태로 전달하지 않았다.

협력사는 기존 평문 topic을 읽는 Consumer들의 중복 복호화 구현을 피하기 위해 별도 Bridge 구조를 제안했다. 나는 해당 구조에서 필요한 실행환경과 호출 조건을 확인했다. 운영 Bridge의 Kafka 설정·offset·DLT 정책 전체를 직접 개발했다는 의미는 아니다.

## 3. 개발 결과와 전달 자료의 불일치 점검

당시 요청 기록에는 다음 검토가 남아 있다.

- Node-RED에서 호출하려면 애드온과 wrapper가 필요한지, 전달본에 반영됐는지 질문
- 호출 예제와 파일별 역할 설명 포함 요구
- 실제 배포물·API와 Markdown 문서 사이의 차이 점검 요청
- 외부에서 얻은 코드 조언을 개발도구에 전달해 타당성 검토·수정·문서 재점검 요청
- 적용 담당자가 읽을 핵심 문서 중심으로 통합·표현 수정 요구

대응 변경에는 Node 타입 선언과 실제 export의 정합성 보완, keyId 길이 검사, Java의 명시적 keyId 지정 API, 종료된 context의 재사용 차단이 포함됐다. 내가 직접 모든 결함을 발견하고 수정했다는 주장과 구분한다.

## 4. 사양별 전달물과 시험 범위 정리

보관된 후보 배포물은 Edge와 Bridge의 바이너리를 분리하고 Node wrapper, Java JAR/JNI, 공개 C 헤더, 호출 예제, 가이드, manifest와 checksum을 포함한다.

초기 요구는 Node-RED 팔레트 노드 형태였다. 이후 작업 기록에서는 라이브러리 호출·상호운용 확인에 초점을 맞춰 전달 범위를 정리했고, 후보 배포물에는 설치형 custom node와 완성된 운영 Bridge가 없다. 초기 요구의 모든 항목을 충족하거나 협력사가 변경 범위를 최종 수용했다고 단정하지 않는다.

보관된 시험 문서에는 대상 이미지 내 로딩·상호운용과 오류 입력 거부 등의 PASS가 적혀 있다. 이는 문서로 남은 기존 시험 기록이며, 고객 현장에서 직접 시험한 실적이 아니다.

## 5. 전달과 수령, 적용 완료의 구분

사용자가 제공한 메일에는 모듈 개발 완료·전달 안내와 협력사의 수령 확인이 있다. 따라서 이전 정리에서 미확인이었던 **모듈 전달·수령**은 사용자 제공 메일 내용으로 보완할 수 있다.

수령 회신은 적용·시험을 진행하겠다는 내용이다. 실제 설치 성공, 운영 배포, 수용 시험 통과 또는 이후 장애 대응 완료를 입증하지 않는다. 메일의 날짜와 첨부파일 checksum이 없어 현재 보관된 후보 파일과 수령 파일의 동일 revision도 확정하지 않았다.

## 지원 직무와 연결되는 경험

기존 C 모듈의 호출 구조를 이해하고, 실제 실행환경과 버전을 확인하며, 구성 누락과 문서·API 차이를 검토하고, 수정·재시험 요구와 적용 방법을 개발도구·협력사 사이에 전달했다. 이 경험은 기존 소프트웨어 이해, 실행환경 분석, 수정 사항 검증 요구, 기술 요구사항 공유 업무와 연결된다.

관련 기술은 C·JavaScript/Node.js·Java·Docker·Linux/Ubuntu다. C++ 빌드 설정이나 Python 보조 도구의 존재만으로 해당 언어를 직접 개발한 경력으로 확대하지 않는다.

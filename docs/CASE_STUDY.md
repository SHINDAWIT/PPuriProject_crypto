# 환경 변경에 대응한 암호 모듈 개발·연동 사례

[처음으로](../README.md) · [검증 결과](VALIDATION.md) · [협의 기록](COMMUNICATION.md)

## 목적과 담당 범위

연구실의 기존 C 기반 ARIA 모듈을 Edge의 Node-RED와 수신 측 Java Bridge에서 호출할 수 있도록 연동 모듈과 바이너리 패키지를 준비했다.

협력사에 적용 구간, 직렬화 시점, 데이터 타입, 실행 이미지, Java 버전과 호출 위치를 질의했다. 회신 내용을 개발 요구사항으로 정리하고, 전달본의 애드온·wrapper·예제·설명 누락 가능성을 검토했다. 문서·API 불일치 점검과 수정, 대상환경 재빌드·시험에는 AI 개발도구를 활용했으며, 개발한 모듈을 협력사에 전달했다.

동료와 함께 진행한 과제다. 코드 작성부터 수정·시험·패키징까지 AI 개발도구를 활용했다.

## 1. 정보가 변경되거나 구체화될 때 빌드 기준 다시 확인하기

| 쟁점 | 초기 정보와 후속 협의 | 대응 |
|---|---|---|
| Node-RED 이미지 | 초기 회신은 latest, 후속 회신은 4.0.5와 고정 digest | 이미지 식별을 구체화하고 재현 가능한 빌드 기준을 고정 |
| Java 런타임 | 초기 Spark Java 8, 후속 회신은 Java 21 마이그레이션 완료. Broker Java 8, Bridge Java 21 | Spark·Broker·Bridge를 구분하고 JNI를 실제 로드할 Bridge의 Java 버전을 확인 |
| payload 타입 | Object 생성 후 후속 단계로 전달하며, 송신 직전 JSON.stringify로 직렬화하는 흐름 | 생성 시점의 객체와 암호화 호출 지점의 직렬화된 데이터를 구분 |
| 호스트와 컨테이너 | Ubuntu 호스트 안에서 Node-RED 컨테이너 실행 | native 바이너리의 기준은 모듈을 로드하는 실행환경. Edge musl과 Bridge glibc 바이너리 분리 |

Java 마이그레이션에 따른 버전 변경을 반영하고, latest로만 전달받았던 이미지는 고정 digest로 구체화했다. 필요한 정보를 추가로 질의해 실제 모듈이 로드되는 구성요소와 버전을 빌드 기준으로 정리했다.

## 2. 기존 모듈과 언어별 호출 경계 구성

~~~text
공통 C ABI
  ├─ Node N-API addon → JavaScript wrapper → Node-RED 호출 지점
  └─ Java JNI → API JAR → 별도 Bridge 프로세스
~~~

기존 C 코어를 공통 C ABI로 노출하고 Node·Java 어댑터에서 호출하도록 구성했다. 두 언어의 호출 계층이 같은 암호 구현을 사용한다.

협력사는 기존 평문 topic을 읽는 Consumer들의 중복 복호화 구현을 피하기 위해 별도 Bridge 구조를 제안했다. 나는 해당 구조에서 암호 모듈을 호출하는 실행환경과 조건을 확인했다. 운영 Bridge의 Kafka 설정·offset·DLT 정책은 연동 시스템에서 별도로 다루는 범위다.

## 3. 개발 결과와 전달 자료의 불일치 점검

전달본을 준비하며 다음 항목을 검토하고 개발도구에 반영을 요청했다.

- Node-RED 호출에 필요한 애드온·wrapper 구성과 전달본 포함 여부
- 호출 예제와 파일별 역할 설명
- 실제 배포물·API와 Markdown 문서의 일치 여부
- 외부 코드 검토 의견의 타당성과 수정 후 문서 정합성
- 적용 담당자가 사용할 핵심 문서의 구성과 설명

검토와 수정 과정에서 Node 타입 선언과 실제 export의 정합성, keyId 길이 검사, Java의 명시적 keyId 지정 API, 종료된 context의 재사용 차단을 보완했다.

## 4. 사양별 전달물과 시험 범위 정리

보관된 후보 배포물은 Edge와 Bridge의 바이너리를 분리하고 Node wrapper, Java JAR/JNI, 공개 C 헤더, 호출 예제, 가이드, manifest와 checksum을 포함한다.

초기 요구는 Node-RED 팔레트 노드 형태였다. 이후에는 라이브러리 호출·상호운용을 중심으로 패키지를 구성했다. 보관된 후보 배포물에는 설치형 custom node와 완성된 운영 Bridge가 없으며, 이 구성과 초기 요구의 차이는 후속 협의 항목으로 남아 있다.

배포 패키지의 시험 요약에는 대상 이미지 내 로딩·상호운용과 오류 입력 거부 등의 PASS가 기록되어 있다. 시험 요약의 생성 방식과 대상환경은 [시험 문서](VALIDATION.md)에 정리했다.

## 5. 모듈 전달과 후속 적용·시험

개발한 모듈을 협력사에 전달하고, 적용·시험 중 발생하는 문제와 개선 사항을 회신해 달라고 요청했다. 협력사는 파일 수령을 알리고 적용·시험을 진행하겠다고 회신했다.

전달 이후의 현장 적용·수용 시험 결과는 이 저장소에 포함되어 있지 않다.

## 프로젝트에서 얻은 경험

기존 C 모듈의 호출 구조를 이해하고, 실제 실행환경과 버전을 확인하며, 구성 누락과 문서·API 차이를 검토하고, 수정·재시험 요구와 적용 방법을 개발도구·협력사 사이에 전달했다. 이 경험은 기존 소프트웨어 이해, 실행환경 분석, 수정 사항 검증 요구, 기술 요구사항 공유 업무와 연결된다.

관련 기술은 C·JavaScript/Node.js·Java·Docker·Linux/Ubuntu다.

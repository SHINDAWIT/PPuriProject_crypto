# 협력사와의 요구사항 확인·전달 이력

[처음으로](../README.md) · [개발 사례](CASE_STUDY.md)

## 메일을 공개하는 방식

**원본 메일은 공개하지 않고, 기술적 판단에 필요한 사실만 익명 요약했다.** 연락처·서명·상대 담당자·회사·수요 업체명·데이터맵·Flow 첨부물·실제 데이터 식별자는 제거했다.

아래 근거는 사용자가 이번 정리에 제공한 메일 본문이다. 원본 메일 파일·헤더·첨부파일의 진위나 날짜를 별도로 검증한 기록은 아니다. 순서는 제공된 대화 순서이며 임의의 발송 날짜를 붙이지 않았다.

## 주요 확인 과정

| 순서 | 주체와 확인 내용 | 정리된 요구·결과 |
|---|---|---|
| E01 | 연구실 측: Edge→Kafka 구간과 Gateway→Client 구간의 암호 적용 범위 질의 | 적용 구간, 대상 데이터, Node-RED 모듈과 가이드의 제공 범위 확인 요청 |
| E02 | 협력사: Edge 송신·수신 측 복호화 구조와 대상 데이터 범위 회신 | Gateway→Client는 HTTPS를 적용하는 프로젝트 범위로 정리. Node-RED 팔레트 노드와 키 사용 가이드 요구 |
| E03 | 연구실 측: Node·N-API·이미지·Flow·payload 타입과 Consumer 런타임·호출 위치 질의 | 기존 시스템에 맞는 개발 언어·배포 형식·호출 경계를 결정하기 위한 정보 요청 |
| E04 | 협력사: Node 20.18.0·N-API 9·latest 이미지·Spark Java 8 등의 정보 회신 | 별도 Bridge를 통한 복호화 후 기존 topic 재전송을 협력사가 제안 |
| E05 | 연구실 측: latest의 실제 이미지 식별과 Bridge 실행 Java 버전 재질의 | 모듈을 실제 로드하는 환경을 고정하기 위한 추가 확인 |
| E06 | 협력사: 고정 Node-RED 4.0.5 digest 및 시스템별 Java 버전 회신 | Spark Java 21 마이그레이션 완료, Broker Java 8, Bridge Java 21로 구분 |
| E07 | 연구실 측: 개발 모듈 압축파일 전달, 적용·시험 중 문제와 개선 사항 회신 요청 | 모듈 전달 메일 내용 확인 |
| E08 | 협력사: 파일 수령 확인, 적용·시험을 진행하겠다고 회신 | 수령 확인. 실제 시험 결과 또는 수용 완료 회신은 아님 |

## 역할과 성과를 정정한 부분

- Bridge 아키텍처의 제안 주체는 협력사다. 본인은 이를 독자적으로 최초 설계한 사람으로 표현하지 않았다.
- 모듈 개발·전달을 목적으로 진행한 과제다. 본인 역할을 정보 전달만으로 축소하지 않고 환경 확인·개발 요구·전달본 검토·개발도구 활용·모듈 전달을 함께 적었다.
- 모듈 전달과 수령은 메일 내용에서 확인된다. 협력사의 실제 적용·시험 성공은 확인되지 않는다.
- 당시 코드·시험 파일과 Git 변경은 기술적 산출물의 존재를 보여준다. 커밋 계정이 같다는 이유로 모든 구현·실행을 개인 수작업으로 귀속하지 않았다.
- 초기 팔레트 노드 요구와 최종 후보의 라이브러리·wrapper 구성에는 차이가 있다. 수령 확인만으로 해당 차이의 최종 승인이나 초기 요구 전체 충족을 주장하지 않았다.

HTTPS 적용은 이 프로젝트의 적용 구간 합의다. 모든 시스템에서 HTTPS만 있으면 payload 암호화나 저장 데이터 보호가 불필요하다는 일반 원칙으로 확대하지 않는다.
